# Voice Input Specification

Status: Implemented

This is the durable product contract for Speaker's macOS voice-input experience. Production release gates remain in the [production-readiness checklist](../production-readiness.md).

## Problem Statement

People want to speak from any macOS work context and receive usable text at the position they selected when they finished speaking. Built-in dictation does not combine user-owned providers, a Personal Dictionary, optional refinement, inspectable Stage Results, and conservative cross-application delivery.

Speaker must make the entire Voice Input Session legible without turning an uncertain target or provider outcome into apparent success. A successful transcript must remain recoverable even when automatic delivery is unsafe.

## Solution

Speaker is a menu-bar macOS application. Holding or short-pressing the configured shortcut starts recording; releasing it freezes the Input Target. The selected Speech Recognition Provider receives the audio: Doubao streams while recording; OpenAI and Qwen use the selected Speech Recognition Method to stream live audio or submit a complete in-memory recording after local validation. Default Smoothing uses the recognition result directly. A non-default Refinement Mode sends that confirmed text, never the audio, for optional further refinement.

Delivery mutates the frozen Input Target only after it remains safe and current. Every compatible nonsecure target uses the same target-revalidated transactional Command-V path, independent of application identity. Accessibility is used only for transient focus and security evidence. A secure, changed, closed, or otherwise uncertain target produces a Pending Copy Result only before delivery commits; an already posted paste command is never presented as safe to repeat manually.

## User Stories

1. As a user, I want Speaker to live in the menu bar, so that voice input stays available without occupying the Dock.
2. As a first-time user, I want Microphone and Accessibility onboarding, so that I understand each permission before granting it.
3. As a user, I want missing or revoked permissions reported explicitly, so that platform failures are not confused with provider failures.
4. As a user, I want `Fn` as the default voice shortcut, so that recording requires minimal hand movement.
5. As a user, I want to select a safe key chord or dedicate one physical Option, Control, or Shift key, so that I can avoid hardware or system conflicts.
6. As a user, I want real shortcut registration to reject conflicts, so that a saved shortcut is actually usable.
7. As a user, I want press/release and short-press interactions to create at most one Voice Input Session, so that repeated events cannot race.
8. As a user, I want `Esc` to cancel an active session or dismiss its retained result or problem, so that accidental input and obsolete prompts do not interrupt my work.
9. As a user, I want clear recording and processing status without focus activation, so that Speaker never changes the intended Input Target.
10. As a user, I want short recordings to end silently and definite digital silence rejected locally, so that accidental taps do not produce a prompt or meaningless delivered text.
11. As a user, I want the Input Target frozen when recording ends, so that later window changes never retarget my result.
12. As a user, I want password fields and other secure targets excluded from automatic delivery and text history, so that sensitive work stays protected.
13. As a user, I want unsupported, changed, closed, or unverifiable targets to produce a Pending Copy Result, so that usable text is never lost or inserted into the wrong place.
14. As a user, I want copying a Pending Copy Result to be explicit and verified, so that I control when a retained result remains on my clipboard.
15. As a user, I want Default Smoothing to use the selected Speech Recognition Provider only, so that the normal path avoids a second provider.
16. As a user, I want punctuation, written-form number normalization, and light disfluency removal, so that ordinary dictation is immediately usable.
17. As a user, I want concise cleanup, full rewrite, and Custom Modes, so that I can choose how strongly a transcript is refined.
18. As a user, I want every Refinement Mode to preserve the source language, facts, names, numbers, and intent, so that refinement cannot invent content.
19. As a user, I want the selected Refinement Provider used only by modes that require further refinement, so that audio and Default Smoothing never reach the selected Refinement Provider.
20. As a user, I want every Refinement Provider failure to fall back to the confirmed recognition Stage Result, so that optional refinement cannot lose a transcript.
21. As a user, I want to supply my own provider credentials and keep them in Keychain, so that Speaker has no shared provider backend or embedded secret.
22. As a user, I want content-free provider diagnostics and connection checks, so that configuration and transport problems are actionable without exposing audio or text.
23. As a user, I want a local Personal Dictionary of names and specialist terms, so that those words are recognized more accurately.
24. As a user, I want empty and duplicate Entries rejected and each session to use a stable dictionary snapshot, so that edits remain deterministic.
25. As a user, I want the Entries of my Personal Dictionary carried into the selected Refinement Provider refinement as text, so that a misheard term can be corrected to my spelling even when recognition alone failed.
26. As a user, I want the selected Refinement Provider instructed to keep mixed Mandarin-English speech in each segment's original language and to correct only spans that plausibly match an Entry, so that refinement never translates my words or inserts an Entry I did not say.
27. As a user, I want Settings to show how many Entries will be sent to recognition out of the 100-Entry application capacity and mark every omitted Entry, so that provider limits are visible before my next session.
28. As a user, I want advisory guidance for Entries that contain one character or at least 10 characters after trimming, without blocking save or rewriting the Entry, so that I can improve recognition while retaining my spelling.
29. As a user, I want expanded Session Records to prioritize the retained result and reveal distinct Stage Results and diagnostics on demand, so that I can read and copy text without duplicate content or unrelated editing controls.
30. As a user, I want Session Records with Stage Results, Refinement Mode, timing, and explicit recording or provider errors, so that I can recover text and understand failures without interpreting paste-success assessments.
31. As a user, I want to search, inspect, copy, delete, and clear Session Records, so that local history remains useful and controllable.
32. As a user, I want history retention to follow an explicit policy with a safety cap, so that storage behavior reflects my intent.
33. As a user, I want raw audio, credentials, AX objects, captured source text, and clipboard contents excluded from persistence, so that local diagnostics remain minimal.
34. As a user, I want login launch to be optional and disabled by default, so that Speaker changes startup behavior only with consent.
35. As a user, I want User Cancellation and late provider results handled deterministically, so that stale text can never be delivered.
36. As a user, I want Waiting For Result to remain honest until the provider or system reports an outcome, so that elapsed time is not misreported as a failure.
37. As a user, I want a reproducible build, test, installation, and release path, so that the application can be verified from source and safely distributed.
38. As a user, I want one Microphone Preference available in the menu bar and Settings, defaulting to follow the system, so that I can choose an input without changing other applications.
39. As a user, I want the selected microphone frozen for a Voice Input Session and its loss reported explicitly, so that Speaker cannot silently record from another source.
40. As a user, I want a short local microphone level test that sends no audio to a provider, so that I can check the input before using voice recognition.

## Implementation Decisions

- Speaker targets macOS 14 or later and uses Swift 6. It is a menu-bar application outside App Sandbox because global shortcut monitoring and cross-application Accessibility delivery are core behavior.
- Accessibility and Microphone are the only runtime permissions required for voice input. Shortcut activation and permission recovery are coordinated as one ordered feature lifecycle.
- Onboarding has three explicit steps: Microphone and Accessibility permissions, Speech Recognition Provider configuration, then keyboard shortcut practice instructions. It requests only the permission the user chooses, explains the exact System Settings action, and advances only when the user clicks Next. Permissions must be observed as granted. Doubao retains its explicit connection-check requirement; OpenAI and Qwen require a saved Key and clearly state that availability is first verified during actual recognition. Back and Skip remain available; no provider check runs automatically. Credential writes in progress block first-time completion. Users who completed or deferred setup can reopen “使用引导…” from the menu and browse every step without repeating connection checks; recording readiness remains unchanged. Short-press, hold, and Escape instructions name the physical keyboard shortcut and are not displayed beside the shortcut-recording control. Onboarding and Settings share the same provider credential card. The secure credential editor remains available after a Key is saved or a connection check fails. Saving a replacement clears the draft and invalidates prior verification; Doubao requires a new explicit connection check. Recovery for microphone permission opens Permissions; unavailable microphone problems open Microphones; provider credential and resource problems open API Key settings. Recovery actions remain bound to their originating session.
- The selected `Fn` or side-specific modifier is consumed as Speaker's dedicated trigger without changing macOS global keyboard preferences. Left and right Option, Control, and Shift remain distinct; Command alone is rejected. Key-chord registration continues through Carbon.
- The Voice Input Session module is the primary deep module. Its interface accepts semantic intents and publishes observable session behavior; it hides event ordering, recording, target capture, provider processing, delivery, cancellation, cleanup, and history settlement.
- Commands are serialized. Duplicate edges are idempotent, asynchronous work carries session identity, and late results from cancelled or superseded sessions are discarded.
- The Microphone Preference defaults to following the current system input and may instead identify one input device. The menu and Settings observe one selection model. Device discovery failures, an empty directory, and a missing fixed device are distinct states; a missing fixed choice remains selected and refuses recording. Only its UID is persisted in owner-only settings; hardware names and identities never enter Session Records, provider requests, or copied diagnostics.
- A recording press captures an immutable audio start plan from the latest observed device snapshot before asynchronous session preparation. Device binding and verification happen before audio is streamed; a changed or unavailable selected device fails closed. Selection changes during recording affect the next session. Loss of the actual route or sleep stops the current capture; reconnecting or waking never resumes it. Speaker never changes the system-wide default input.
- Settings exposes an explicit local level test that lasts at most eight seconds and can be stopped. It discards in-memory samples and never creates a provider request or Session Record. Normal voice recording ends a running test before taking the input; late test cleanup cannot stop that new recording.
- Audio capture uses the raw input path and does not request Apple voice processing; the capture environment snapshot records that fact. The resulting audio is converted to 16 kHz, 16-bit, mono PCM in memory and placed in a bounded stream. It is never persisted as a normal application artifact.
- An audio-engine configuration notification revalidates the active capture. Voice input and local level testing continue only while the engine is running, the frozen microphone remains available and bound, and the input format still matches the installed tap. A delayed notification from an unchanged startup does not become a Session Problem; stopped or changed capture ends without automatic restart or fallback.
- Audio streams over Doubao's bidirectional `bigmodel_async` WebSocket while recording. Release sends the final audio frame and begins final-result settlement; the selected resource must match the user's activated provider resource. Speaker does not send a request language and relies on the provider's default Chinese-English model, so mixed Mandarin-English speech is transcribed by that single model.
- A press snapshots the Speech Recognition Provider profile, Refinement Mode, and Personal Dictionary. Release freezes only the frontmost process without AX IPC; immediately after the event callback returns, Speaker reads that process's current focused element or focused window and creates the one-session Input Target token. Delivery later validates that exact target rather than maintaining an application focus cache.
- The Personal Dictionary is local. Entries are sent as request-scoped Doubao direct hotwords or as recognition context for OpenAI and Qwen; Speaker does not apply local alias replacement to the confirmed transcript. Settings derives its sent count and omitted Entries from the same `DictionaryRequestContextBuilder` used for recognition requests. It shows the 100-Entry capacity, marks Entries beyond it as unsent, and presents advisory quality guidance when a trimmed Entry contains one character or at least 10 characters. Guidance never blocks saving or rewrites an Entry. Personal Dictionary editing is available in Settings; history has no Entry creation action. A non-default Refinement Mode also carries the press-time snapshot's Entry words into the refinement request as text: the full snapshot, not the Doubao capacity-truncated list, subject to the encoded request bound. The Session Record keeps the recognition dictionary request context.
- Default Smoothing does not call the selected Refinement Provider. It enables Doubao semantic smoothing for Doubao and uses direct recognition output for OpenAI and Qwen; it does not promise equivalent cleanup across providers. Non-default Refinement Modes disable Doubao semantic smoothing so the confirmed recognition Stage Result remains a more faithful refinement source; punctuation and written-form number normalization remain enabled. Those modes send only that text, the selected rule, and the Entry words of the press-time Personal Dictionary snapshot through a non-streaming JSON request; each is a labeled data-only JSON string block, and an empty dictionary omits its block entirely. The fixed instructions cast the selected Refinement Provider as a dictation editor: every fact traces to the source, questions stay questions, the speaker's person and tone survive, mixed Mandarin-English text keeps each segment's spoken language without translation, a self-correction keeps only the corrected wording, and an Entry spelling replaces only a span that is phonetically or visually close to it, never an insertion where the source has no such span. Only a bounded, non-empty normal completion with the expected shape may replace the recognition Stage Result.
- API Key cards group secure entry, save or replacement, and confirmed deletion together. A failed save retains the editable draft and displays the error; successful replacement clears the draft and invalidates connection verification. Concurrent credential changes are refused while a save or deletion is pending. Refinement cards show one highlighted card. Opening the Custom Mode editor moves the highlight to Custom Mode, while the checkmark continues to identify the active Refinement Mode. An inactive custom editor states that saving and enabling is required and names the currently active mode; unfinished drafts never change processing.
- Provider credentials live in Keychain. Settings, the Personal Dictionary, Session Records, and development credentials use owner-only persistence appropriate to their data type.
- Expanded history shows the full retained result once, with compact metadata above it. Normal records have no success, delivery, pending-copy, or unconfirmed status. Only explicit recording, recognition, or refinement errors receive an error label; textless errors remain visible, while accidental short recordings and empty provider results stay quiet. Distinct Stage Results and recording/provider diagnostics are separately collapsed until requested; identical text is not repeated. Collapsed rows retain their bounded previews and stable hover geometry. Copy uses the complete retained text.
- Session Records use versioned SQLite transactions. Secure targets never persist transcript text or provider request identifiers, including non-terminal and cancelled records.
- Delivery is conservative and application-independent. Accessibility freezes and validates the transient Input Target but never writes its text. Clipboard enumeration failure is distinct from a valid empty clipboard and refuses both automatic delivery preparation and explicit copy before any clipboard mutation. One paste transaction snapshots all readable pasteboard representations, carries a private ownership marker, preflights event-post access, posts exactly one physical Command-V from the combined login-session event state, and restores only while the pasteboard still belongs to Speaker. Target-confirmed insertion and posted-without-receipt are distinct outcomes; neither can be retried after commit. Speaker does not restore focus, rewrite an entire rich document, or overwrite a newer user clipboard value.
- A Pending Copy Result is a successful recovery surface, not a generic failure. Its non-activating presentation exposes explicit copy, retry, and dismiss actions tied to the originating session. Copy failure keeps the complete text, shows an inline failure message and a retry-copy control in the same compact capsule, and closes only after a successful retry or explicit dismissal. Starting another recording also dismisses the old result immediately; there is no separate temporary-result archive. Recovery from history depends on retention settings, the Input Target's security class, and successful persistence.
- The too-short recording outcome closes the HUD and produces no menu or VoiceOver warning; its existing Session Record remains available. Other capture failures retain their normal problem presentation. Escape dismisses the currently owned Pending Copy Result or Session Problem through the same global trigger path used for cancellation. Dismissal never retries delivery or affects a later session, including while an earlier session finishes cleanup. Problem and recording HUDs use the same close control.
- User Cancellation is distinct from a Session Problem. Cancellation closes the user-facing session immediately; a mutation that already committed may finish its receipt and history settlement but cannot be rewritten as cancelled.
- Hovering the recording HUD reveals cancellation on the left and an end-recording action on the right while retaining the live waveform. Ending recording from the HUD freezes the Input Target at that action and enters the same processing and delivery path as the shortcut. Actions belong to their originating session; repeated or stale completion actions cannot stop another session. Processing exposes cancellation only. A Pending Copy Result uses a compact text capsule with an explicit copy icon and a hover-revealed dismiss action. Successful automatic delivery still closes the HUD without a completion prompt.
- Application shutdown fences new shortcut intake, stops session dispatch, cancels external work, and waits for required local persistence in that order.

## Testing Decisions

- Good tests cross the same interface as production callers and assert externally observable behavior rather than private method calls, internal state layout, or framework call counts.
- The highest test seam is the Voice Input Session interface. Deterministic adapters replace recording, target capture, the selected Speech Recognition Provider, the selected Refinement Provider, delivery, time, clipboard, and persistence behind that seam.
- Session specifications cover shortcut ordering, duplicate edges, short recordings, definite silence, snapshots, target timing, provider outcomes, optional refinement, fallback, User Cancellation, stale results, secure and changed targets, Pending Copy Results, explicit copy, history, and shutdown.
- Provider adapter specifications verify request framing, credential placement, resource/model selection, response decoding, cancellation, stable error classification, content bounds, and secret exclusion without contacting paid endpoints.
- Persistence specifications exercise in-memory and temporary-disk adapters through the same interfaces. They cover schema migration, retention, search, deletion, secure-target redaction, corruption recovery, owner-only file handling, and sensitive-content exclusion.
- App scenario specifications verify product rules without a window server, including Personal Dictionary capacity and advisory save behavior. AppKit UI specifications verify production window configuration, non-activation, geometry, accessibility, layout transitions, and Entry status guidance.
- Platform behavior without a cross-application Apple contract is accepted through the [real-machine compatibility matrix](../compatibility.md), not through a fake that claims universal support.

## Speech Recognition Provider selection

- Settings and onboarding offer Doubao, OpenAI, and Alibaba Qwen independently of text refinement. Existing installations retain Doubao. Each provider keeps its model choice and Speech Recognition Method; Qwen also keeps an explicit Beijing or Singapore region. Missing method fields preserve the previous behavior: Doubao streams, and OpenAI and Qwen use complete-recording recognition. Settings offers only models compatible with the selected method, and switching methods selects a compatible model without changing the credential namespace. The bundled catalog includes only models whose selected API contract is implemented.
- Configuration is persisted before activation. An invalid restored recognition profile remains selected and refuses recognition until corrected; it never falls back to Doubao. The Voice Input Session snapshot fixes provider, method, model, destination, and credential namespace. Credentials are loaded from that namespace; no missing Key, failed request, or unavailable model causes a cross-provider or cross-region fallback.
- OpenAI recognition has a separate credential namespace from OpenAI text refinement. Qwen regions have separate Keys. Saving, switching, refreshing settings, and startup never send a recognition probe. Concurrent configuration and credential mutations are excluded, and stale async work cannot change a newer selection.
- Complete-recording recognition uses multipart WAV transcription for OpenAI and synchronous compatible-mode audio input with an in-memory Base64 WAV for Qwen. Ending the PCM stream alone never authorizes upload: the recording completion gate must confirm successful local capture validation first; failure and cancellation reject the gate. OpenAI supports at most five minutes and Qwen at most three minutes per recording in this implementation; Qwen's shorter application bound keeps the encoded request below its API size limit. Oversize audio fails without truncating or sending a partial transcript. Responses are bounded before decoding, redirects are refused, and only complete successful text can reach refinement and delivery.
- Streaming recognition uses dedicated realtime WebSocket APIs and models. It sends audio while recording, receives intermediate events concurrently, and disables automatic turn detection. Only successful local capture completion authorizes the final manual audio commit. The adapter accepts the confirmed text for that committed audio; intermediate text never enters refinement, delivery, or history. OpenAI receives 24 kHz PCM converted in memory; Qwen receives the captured 16 kHz PCM. Streaming retains the same five-minute OpenAI and three-minute Qwen application bounds. Cancellation closes the connection and discards late results, but cannot recall audio already sent. No automatic method fallback or duplicate full-recording pass occurs.
- Default Smoothing produces no additional text-refinement request. Personal Dictionary context is advisory recognition data; no local alias replacement or cross-provider retry is performed.
- Session Records retain recognition provider and model attribution, including cancellation and explicit failures. Missing legacy attribution keeps its historical interpretation. Existing serialized stage-text field names remain compatible and do not determine the current provider.
- Offline specifications verify provider selection, credentials, request formats, response acceptance, cancellation, snapshot ownership, persistence, and UI behavior. Live account permissions, recognition accuracy, network latency, and cost remain separate acceptance evidence.

## Refinement Provider selection

- Settings offers DeepSeek, OpenAI, Kimi, GLM, and Custom. Built-in model lists and defaults are maintained in `RefinementProviderCatalog` and shipped with the App; no remote catalog request or refresh action is used. The first listed model is recommended and is the default for an unconfigured provider. Recommendations prioritize cost and the text-only JSON request contract. GLM `glm-5.3-flash` enables mandatory thinking with `reasoning_effort: low` and an 8,192-token completion budget; reasoning content is ignored and cannot substitute for a complete final JSON answer. Other built-in defaults disable thinking. Every provider still accepts a manually entered model ID. Saved choices remain selectable and are never replaced merely because the bundled recommendations change. Custom requires an HTTPS base URL and model ID; Speaker appends `/chat/completions`.
- OpenAI's bundled GPT-5.6 models explicitly disable reasoning with `reasoning_effort: none`. Older or unknown manually entered models do not receive that parameter. Manual model IDs remain subject to the selected provider's request profile and are not a compatibility guarantee.
- Each provider retains its own Key and model across provider switches and application restarts. Changing a model within the same provider reuses that provider's Key. Saving or deleting a Key changes only the selected provider's credential; a blank Key draft does not mean the saved credential was removed. Built-in endpoints are fixed. Custom has one configuration slot, and its Key ownership includes the normalized destination, so an address change requires an explicit Key save before requests resume. Redirects are refused, and Speaker never retries against another provider or region.
- Switching provider/model clears connection verification and the Key draft. Saving configuration precedes live activation. An unconfigured selection uses Default Smoothing while retaining the preferred Refinement Mode for restoration after a Key is saved. No automatic connection checks occur; the explicit check states that it sends synthetic text and may incur cost.
- The press-time snapshot freezes provider/model/destination for the active session. Settings changes apply to later sessions. Session Records attribute results to that snapshot; legacy records retain their DeepSeek interpretation.
- Requests contain at most 256 KiB encoded data and responses at most 1 MiB before decoding. Oversize input is not truncated. Only `finish_reason = stop` with no refusal/tool call and exactly one non-empty JSON `text` value may replace the recognition Stage Result. All explicit failures preserve that result; cancellation never delivers a late result.
- Deterministic specifications cover credential isolation, destination changes, model retention, stale-check fencing, atomic mode activation, snapshot ownership, and history attribution. Live provider quality remains a separate approved acceptance run.

## Out of Scope

- Showing elapsed waiting time or manually accepting the confirmed recognition Stage Result while refinement is pending. Processing retains its compact waveform and cancellation control.
- Accounts, a hosted Speaker backend, cloud history, cloud settings, multi-device sync, subscriptions, teams, or shared dictionaries.
- Offline transcription, ASR providers beyond Doubao/OpenAI/Qwen, translation, text-to-speech, meeting transcription, diarization, or long-form audio management.
- Saving or replaying raw audio.
- Persistent or unconditional clipboard replacement, forced focus restoration, or guaranteed delivery into every macOS input control.
- Per-application Refinement Modes or Personal Dictionaries, dictionary synchronization, and cloud history backup.
- iPhone or iPad application targets.
